Potentials
==========

The pyMCPU energy is a sum of knowledge-based table lookups. Each term
is a :py:class:`~pymcpu.mcpu_core.Potential` object registered on a
:doc:`System <system>`, which owns it and evaluates it. Every potential
carries an integer *energy group*; the group selects the outer weight
applied to that term's raw value.

.. note::
   Energies are **unitless** sums of knowledge-based potential table
   entries. There is no kT, no Boltzmann constant and no Kelvin
   anywhere in the engine, and the outer weights below are likewise
   dimensionless.

.. note::
   Every class on this page lives in the compiled ``pymcpu.mcpu_core``
   extension module. The documentation build mocks that module (Read
   the Docs cannot compile the C++20 extension), so the directives here
   are hand-authored rather than generated by ``autodoc``. Signatures
   were read off the built extension; none of these classes carries a
   docstring unless one is quoted below.

Base class
----------

.. py:currentmodule:: pymcpu.mcpu_core

.. py:class:: Potential

   Abstract base of every energy term. It is exposed only so that
   ``isinstance`` checks and the ``System`` registry have a common
   type: it has no Python constructor, and ``Potential()`` raises
   ``TypeError: pymcpu.mcpu_core.Potential: No constructor defined!``.

   ``Potential`` is *not* re-exported at the top level; reference it as
   ``pymcpu.mcpu_core.Potential``.

   .. py:method:: get_energy_group() -> int

      Return the energy group this potential contributes to.

   .. py:method:: set_energy_group(group_id, /) -> None

      Assign the energy group. ``group_id`` is positional-only --
      pybind11 exposes no keyword name for it.

   .. py:method:: get_name() -> str

      The term's name, or ``''`` if it has none.

   .. py:method:: set_name(name) -> None

      Name the term, e.g. ``'mu'``. The force fields name every term they
      create. A name must match ``[a-z][a-z0-9_]*`` and cannot be one of the
      energy CSV's own columns (``step``, ``total``, ``walker_id``,
      ``group_<n>`` or anything ending in ``_accepted``/``_attempted``);
      anything else raises ``ValueError``.

   .. py:method:: is_enabled() -> bool

      Whether the potential is evaluated.

   .. py:method:: set_enabled(enabled) -> None

      Enable or disable evaluation of this term. A disabled potential
      contributes nothing and is skipped entirely.

Physics terms
-------------

.. py:currentmodule:: pymcpu

All five terms below are constructed for you by
``MCPUForceField.create_system()``, which loads the parameter tables
and assigns groups 1-5. Constructing them by hand is only useful when
supplying your own tables.

.. py:class:: MuPotential(energies, dist_sq, hard_core, types, to_residue)

   Pairwise contact ("mu") potential, plus the hard-core overlap test.
   Default energy group **1**.

   :param energies: ``float32`` array of shape ``(m, n)``: the contact
      energy for each atom-type pair.
   :param dist_sq: ``float32`` array of shape ``(m, n)``: squared
      contact distance per atom-type pair.
   :param hard_core: ``float32`` array of shape ``(m, n)``: squared
      hard-core radius per atom-type pair.
   :param types: ``Sequence[int]`` -- per-atom type index.
   :param to_residue: ``Sequence[int]`` -- per-atom residue index.

   .. py:method:: cache_necessary_data(topo_contact_mask, topo_clash_mask, coords) -> None

      Install the topology contact/clash masks and seed the internal
      caches from ``coords`` (a ``float32`` ``(3, n)`` array).

   .. py:method:: set_topology_atom_meta(res_index, is_sidechain, atom_role, res_class) -> None

      Layer 1 per-atom topology metadata for three-layer eval.

      All four arguments are ``Sequence[int]`` of length ``n_atoms``.

   .. py:method:: calculate_energy_change(context, old_state, new_state, patch) -> float

      Incremental energy for one proposed move. Called by the
      integrator; direct use requires a ``ProposalPatch`` built by the
      proposal machinery.

   .. py:attribute:: mu_exact_cutoff

      Read-only. Denselist query cutoff (Å) from
      ``max(type_params_ contact/hard)``.

   .. py:attribute:: mu_cutoff_sq

      Read-only. ``mu_exact_cutoff`` squared, used in the denselist
      ``r²`` prefilter.

   .. py:attribute:: clash_exception_count

      Read-only ``int``. Number of hard-core overlaps seen.

   .. rubric:: Internals and benchmarking

   These are development hooks, not part of the stable API:
   ``use_topo_flags`` (read/write ``bool``, default ``True``; ``False``
   selects the older on-the-fly Layer 1 decode, as does
   ``MCPU_TOPO_FLAGS=0``), ``topo_flag_size_mb``,
   ``type_params_size_kb``, ``verify_layered_eval_consistency()`` and
   ``bench_eval_pair_only(n_iter=1000000)``.

.. py:class:: TripletPotential(loaded_params)

   Backbone triplet torsion term: the knowledge-based
   ``(phi, psi)``-triplet table over consecutive backbone residues.
   Default energy group **2**. See
   :doc:`../physics_notes/triplet_torsion`.

   :param loaded_params: ``Sequence[float]`` -- flattened parameter
      table.

.. py:class:: SidechainTripletPotential(loaded_params)

   Sidechain torsion counterpart of :py:class:`TripletPotential`.
   Default energy group **3**.

   :param loaded_params: ``Sequence[float]`` -- flattened parameter
      table.

.. py:class:: HBondPotential(loaded_params, seq_dep_params)

   Directional hydrogen-bond term. Default energy group **4**. See
   :doc:`../physics_notes/hbond_directional` and
   :doc:`../hbond_legacy_parity`.

   :param loaded_params: ``Sequence[float]`` -- geometric parameter
      table.
   :param seq_dep_params: ``Sequence[float]`` -- sequence-dependent
      parameter table.

.. py:class:: AromaticPotential(aromatic_atom_indices, loaded_params)

   Aromatic ring stacking term. Default energy group **5**. See
   :doc:`../physics_notes/aromatic_stacking`.

   :param aromatic_atom_indices: ``Sequence`` of 3-element integer
      sequences -- the three atoms defining each aromatic ring plane.
   :param loaded_params: ``Sequence[float]`` -- parameter table.

Bias term
---------

.. py:class:: NativeContactsBiasPotential(ca_atom_i, ca_atom_j, q_cutoff)

   Harmonic umbrella on the hard native-contact count ``N``:
   ``U = 0.5 * k * (N - N0)^2``. Energy group **6** by convention.

   ``k`` and ``N0`` are *not* constructor arguments; they are set per
   context with :py:meth:`Context.set_native_contacts_bias`, so one
   registered potential can serve a whole replica ladder.

   :param ca_atom_i: ``Sequence[int]`` -- first atom of each reference
      contact pair, as engine indices in build order (what
      ``forcefield.blocks`` gives). After an ``init_only`` reorder the
      System maps them to storage order when the potential is added.
   :param ca_atom_j: ``Sequence[int]`` -- second atom of each pair.
   :param q_cutoff: ``float`` -- contact distance cutoff in Å. A pair
      counts towards ``N`` when it is closer than this.

   .. py:method:: num_pairs() -> int

      Number of reference contact pairs.

   .. py:method:: initialize_pair_cache(state, cache) -> None

      Seed the per-pair contact cache from ``state``. ``cache`` is a
      ``Sequence[int]`` of length ``num_pairs()``.

   .. note::
      The usual way to attach this term is
      ``pymcpu.sampling.attach_native_contacts_bias_potential(system, cv)``,
      which builds the pair lists from a ``NativeContactsCV``, sets the
      energy group to 6 and registers the potential on the system. It
      requires ``cv.mode == "hard"``.

Energy groups and legacy weights
--------------------------------

``Context`` applies one outer weight per energy group. With
``use_legacy_weights`` left at its default (``True``) the weights
reproduce the legacy MCPU configuration:

.. list-table::
   :header-rows: 1
   :widths: 10 34 18 18 20

   * - Group
     - Term
     - Configured
     - Effective
     - Legacy name
   * - 1
     - :py:class:`MuPotential`
     - 0.4
     - 0.4
     - ``POTNTL_WEIGHT``
   * - 2
     - :py:class:`TripletPotential`
     - 1.35
     - 1.35
     - ``TOR_WEIGHT``
   * - 3
     - :py:class:`SidechainTripletPotential`
     - 2.5
     - 2.5
     - ``SCT_WEIGHT``
   * - 4
     - :py:class:`HBondPotential`
     - 1.35
     - **2.7**
     - ``HBOND_WEIGHT``
   * - 5
     - :py:class:`AromaticPotential`
     - 5.0
     - 5.0
     - ``ARO_WEIGHT``
   * - 6
     - :py:class:`NativeContactsBiasPotential`
     - 1.0
     - 1.0
     - --
   * - 7
     - :py:class:`OrientationalPairPotential`
     - 1.0
     - 1.0
     - --
   * - 8
     - :py:class:`CalphaExcludedVolumePotential`
     - 1.0
     - 1.0
     - --

Group 4 is the one asymmetric row: the configured outer weight is
1.35, but the effective multiplier is ``1.35 * hbond_rdthree`` with
``hbond_rdthree = 2.0`` (legacy ``RDTHREE_CON``), i.e. **2.7**.
:py:meth:`Context.get_energy_weights` reports the *effective* value.
Groups 9-15 are unclaimed and default to 1.0. Note that group 7 is the
last one the engine still times -- ``Context::energy_delta_ns_`` is
``[8]`` -- which is why the expensive KORP term takes it and the cheap
steric filter takes 8.

The constants are exposed on ``pymcpu.mcpu_core.EnergyWeights`` as
``LEGACY_MU``, ``LEGACY_BB_TOR``, ``LEGACY_SC_TOR``, ``LEGACY_HBOND``,
``LEGACY_RDTHREE`` and ``LEGACY_ARO``. Setting
``Context.set_use_legacy_weights(False)`` drops every outer weight to
1.0 and the ``hbond_rdthree`` factor with it.

KORP lineage
------------

These two are a separate force field from the MCPU terms above and are
not mixed with them: :py:class:`~pymcpu.KORPForceField` installs both
and nothing else. See :doc:`/physics_notes/korp_6d`.

.. py:class:: OrientationalPairPotential(map, n_atom, ca_atom, c_atom, korp_type, seq_number, chain_id)

   KORP's 6D orientation-dependent residue-pair energy (energy group 7,
   default outer weight 1.0).

   One frame per residue built from its own N, CA and C; the pair
   coordinate is CA-CA. No sidechain atom is read, which is what makes
   this usable as a backbone-only force field.

   ``korp_type`` indexes KORP's own residue ordering, alphabetical by
   **one-letter** code -- *not* pyMCPU's ``AMINO_INDEX`` ordering.
   ``seq_number`` must be PDB residue numbers: KORP derives sequence
   separation from those rather than from array position, so renumbered
   input genuinely scores differently.

   The energy map is not distributed with pyMCPU. Build this through
   :py:class:`~pymcpu.KORPForceField` rather than by hand.

   .. py:method:: set_rigid_skip_enabled(on)

      Testing hook: disable the moved-moved elision in the incremental
      path, so it enumerates every changed pair instead. Both paths must
      agree on which moves are accepted.

.. py:class:: CalphaExcludedVolumePotential(ca_atom, seq_number, chain_id, min_separation=3, min_distance=3.2)

   CA-CA excluded-volume filter (energy group 8).

   KORP has no hard-core repulsion, so on its own it lets a chain pass
   through itself during MC. This term contributes exactly zero to every
   accepted state and returns the clash sentinel otherwise, so it deletes
   impossible configurations without shifting the ensemble.

   The 3.2 A floor is measured rather than assumed -- see
   :doc:`/physics_notes/korp_6d`. Pairs on different chains are never
   exempt, whatever their residue numbering.

Steric clashes
--------------

There is no separate clash potential. Hard-core overlap is handled
inside :py:class:`MuPotential`: the ``hard_core`` table gives a
squared hard-core radius per atom-type pair, an overlapping pair
contributes a large sentinel energy, and the resulting total is
reported as a hard rejection rather than a finite energy. After a
total-energy evaluation the reason is readable from the context:

.. code-block:: python

   context.calculate_total_energy(-1)
   if context.has_steric_clash():
       print("starting structure has a hard-core overlap")

Both :py:meth:`Context.has_steric_clash` and
:py:meth:`Context.has_hard_constraint_violation` describe the *most
recent* total-energy evaluation, so call
:py:meth:`Context.calculate_total_energy` first. During sampling the
integrator applies the same test itself and rejects the move; see
:py:meth:`Integrator.get_steric_rejected`.

.. seealso::
   To immobilize part of a structure, use
   :py:meth:`Integrator.set_fixed_residues` (or
   ``Simulation.set_fixed_residues()``, which fills in the residue
   count for you). Fixed residues are filtered out of move proposals
   by the integrator, not by a potential. To exclude residues from the
   energy instead of from the moves, see
   :py:meth:`System.set_energy_ignored_residues`.
